SECTION 0 — DOCUMENT RULES

3C. PERMISSION ENFORCEMENT IN .NET API
────────────────────────────────────────────────────────

IMPLEMENTATION:

1. On JWT issuance: load user's permissions from DB → embed in JWT claims
   Claims: [...roles, ...permissions as "permission" claim type]
   Cache permissions in Redis (5-minute TTL) to avoid DB hit per request.
   On role/permission change: invalidate user's Redis cache + force re-auth.

2. Custom permission attribute:
   [RequirePermission("bookings.view")]
   public async Task<IActionResult> GetBookings() { ... }

3. Custom authorization handler:
   PermissionAuthorizationHandler checks "permission" claims in JWT.
   Falls back to DB check if claim missing (handles permission changes mid-session).

4. Resource ownership check (SEPARATE from permission check):
   // Every GET/PUT/DELETE verifies the resource belongs to current user
   // This prevents IDOR (Insecure Direct Object Reference) attacks
   var booking = await _db.Bookings.FindAsync(id);
   if (booking.UserId != currentUserId && !userIsAdmin)
       throw new ForbiddenException("Access denied");

5. Role-specific data filtering:
   // Partners see only their bookings
   if (user.Role == "partner")
       query = query.Where(b => b.PartnerId == currentUser.PartnerId);
   // Technicians see only their assigned bookings
   if (user.Role == "technician")
       query = query.Where(b => b.TechnicianId == currentUser.Id);
   // Support sees masked PII (AutoMapper profile: SupportUserDto masks phone)

6. Response shaping by role (AutoMapper profiles):
   AdminUserDto:       full data including phone, email, DOB
   SupportUserDto:     phone masked (+91 XXXXX XX210), no DOB
   PartnerCustomerDto: name + booking status only

────────────────────────────────────────────────────────
4A. AUTHENTICATION HARDENING
────────────────────────────────────────────────────────

JWT CONFIGURATION:
  Algorithm:          RS256 (asymmetric — NOT HS256)
  Private key:        RSA 2048-bit, stored in Azure Key Vault
  Public key:         Served via /.well-known/jwks.json endpoint
  Access token TTL:   15 minutes
  Refresh token TTL:  30 days (mobile) / 8 hours (admin portal)
  Claims:
    sub:              user.id (UUID)
    jti:              UUID (unique per token — enables blacklisting)
    role:             user.role
    permissions:      array of permission codes
    aud:              "vitalscan-api"
    iss:              "vitalscan-auth"
    device_id:        SHA256(device_info) — for binding
  Signing key rotation: Every 90 days via Azure Key Vault rotation policy

REFRESH TOKEN:
  Generation:         RandomNumberGenerator.GetBytes(64) → Base64
  Storage:            SHA-256 hash stored in DB (never plain text)
  Rotation:           On every use, old token invalidated, new token issued
  Reuse detection:    If revoked token is used again → revoke ALL user tokens
                      → send security alert to user via WhatsApp
                      → log security event
  Device binding:     Refresh token bound to device_id claim
                      If device changes → require full re-auth

OTP SECURITY:
  Length:             6 digits
  Expiry:             5 minutes
  Max attempts:       5 (then lockout)
  Progressive lockout:
    3 failures        → 2-minute wait
    5 failures        → 15-minute wait
    10 failures       → 24-hour lockout (requires CS intervention)
  Rate limiting:      3 OTP sends per mobile per 10 minutes
                      5 OTP sends per IP per 10 minutes
  Storage:            bcrypt hash (never plain OTP in DB)
  Channel:            WhatsApp first, SMS fallback after 30s
  Brute force:        Bot detection via honeypot field in login form (Angular)

ADMIN PORTAL AUTH:
  Method:             Email + password + mandatory TOTP
  Password policy:    Min 12 chars, 1 upper, 1 lower, 1 number, 1 special
  Password storage:   bcrypt cost factor 12
  Failed attempts:    5 attempts → 15-min lockout
  2FA:                TOTP (Google Authenticator / Authy compatible)
                      Mandatory on first login
                      Backup codes: 8 single-use codes issued on enrollment
  Session:            30-minute idle timeout (admin_session_timeout_minutes config)
  IP allowlist:       Optional per super_admin account (Azure Static Web Apps config)

4B. API SECURITY HARDENING
────────────────────────────────────────────────────────

SECURITY HEADERS (added by middleware on every response):
  Strict-Transport-Security: max-age=31536000; includeSubDomains; preload
  X-Content-Type-Options:    nosniff
  X-Frame-Options:           DENY
  X-XSS-Protection:          1; mode=block
  Referrer-Policy:           strict-origin-when-cross-origin
  Permissions-Policy:        camera=(), microphone=(), geolocation=()
  Content-Security-Policy:
    default-src 'self';
    img-src 'self' https://images.unsplash.com https://*.blob.core.windows.net data:;
    font-src 'self' https://fonts.gstatic.com;
    style-src 'self' 'unsafe-inline' https://fonts.googleapis.com;
    script-src 'self';
    connect-src 'self' https://api.anthropic.com;
    frame-ancestors 'none';

CORS:
  Allowed origins (explicit, NO wildcard):
    https://admin.vitalscan.app
    https://vitalscan.app
    http://localhost:4200 (dev only, feature-flagged)
  Methods: GET, POST, PUT, DELETE, OPTIONS
  Headers: Authorization, Content-Type, X-App-Source
  Credentials: true

RATE LIMITING (distributed, Redis-backed, sliding window):

  GROUP: Authentication (strictest)
    POST /auth/otp/send        → 3/10min per mobile + 5/10min per IP
    POST /auth/otp/verify      → 5/5min per session_id
    POST /auth/google          → 10/min per IP
    POST /auth/token/refresh   → 20/min per user

  GROUP: AI (expensive)
    POST /ai/sessions/*/message → 20/hour per user
    POST /ai/sessions           → 10/hour per user

  GROUP: Write operations
    POST /bookings             → 10/min per user
    POST /cart/items           → 30/min per user
    POST /support/tickets      → 5/hour per user

  GROUP: Read operations (authenticated)
    GET  /reports/*            → 30/min per user
    GET  /tests, /packages     → 60/min per user

  GROUP: Public reads
    GET  /config/*, /home/*    → 100/min per IP (backed by Redis cache)

  GROUP: Admin operations
    All /admin/*               → 100/min per admin user
    POST /admin/notifications/broadcast → 2/hour per admin
    POST /admin/reports        → 20/min per admin

  GROUP: Webhooks
    POST /payment/webhook      → 200/min from Razorpay IP allowlist only

  IP BLOCKING:
    100+ rate limit violations in 1 hour → 1-hour IP block (Redis)
    500+ violations in 24 hours → 7-day IP block + alert to admin

INPUT VALIDATION:
  All inputs validated with FluentValidation before processing.
  String fields: max length enforced, HTML stripped (HtmlSanitizer library)
  File uploads:
    MIME type validated server-side (never trust Content-Type header)
    File content inspected (magic bytes check)
    Max sizes:
      Profile photo:  2MB (JPEG, PNG, WebP only)
      Report PDF:     10MB (PDF only)
      Document:       5MB (PDF, JPEG, PNG)
      Banner image:   3MB (JPEG, PNG, WebP)
    Filenames: sanitized, UUID-renamed on storage
  URL fields: validated against SSRF allowlist
  Numeric fields: range-validated
  UUIDs: format-validated before any DB query

SQL INJECTION:
  EF Core parameterized queries used exclusively.
  Raw SQL forbidden. If unavoidable: FromSqlRaw with @params only.
  Regular automated scanning: OWASP ZAP in CI pipeline

MASS ASSIGNMENT PROTECTION:
  Only explicit DTO properties bound in controller actions.
  [ApiController] binding never maps directly to domain entities.
  Update endpoints only accept fields the user is permitted to change.

INSECURE DIRECT OBJECT REFERENCE (IDOR) PREVENTION:
  Every resource access verifies ownership before returning data.
  Pattern (applied to every GET/PUT/DELETE):
    var resource = await _db.FindAsync(id)
                   ?? throw new NotFoundException();
    if (!OwnershipService.CanAccess(currentUser, resource))
        throw new ForbiddenException();
  Consistent 403 response regardless of whether resource exists
  (prevents resource enumeration attacks).

OUTPUT FILTERING:
  AutoMapper profiles per role — different response DTOs per caller role.
  Phone numbers, email, DOB masked in non-admin responses unless
    caller has users.view_pii permission.
  Report content only returned if caller owns the report or is family member.
  Never include: password hashes, OTP hashes, JWT signing keys,
    internal IDs beyond what client needs, stack traces.

ERROR RESPONSES (consistent, no information leakage):
  400: "Validation failed" + field errors (no internal details)
  401: "Authentication required"
  403: "Access denied"          ← NEVER reveal WHY access was denied
  404: "Resource not found"     ← same response whether forbidden or truly not found
  429: "Too many requests. Retry after {seconds}."
  500: "An error occurred. Reference: {correlation_id}"
       ← correlation_id maps to Application Insights log, never exposed details

SWAGGER / API DOCS:
  Enabled: development + staging environments only
  Production: disabled entirely (returns 404)
  Auth required: even on staging, require admin Bearer token to access Swagger UI

PAGINATION:
  All list endpoints enforce pagination.
  Max pageSize: 100 (enforced server-side, never trust client)
  Default pageSize: 20

  NEVER: SharedPreferences, local files, or in-memory only

CODE OBFUSCATION:
  Build command:
    flutter build apk --obfuscate --split-debug-info=./build/debug-info/
    flutter build ios --obfuscate --split-debug-info=./build/debug-info/
  Debug symbols: stored separately, never in app bundle

ROOT / JAILBREAK DETECTION:
  Package: flutter_jailbreak_detection
  On detection:
    - Show warning dialog explaining security risks
    - Disable report viewing (PHI protection)
    - Disable biometric auth (unreliable on compromised devices)
    - Log security event to Application Insights
    - Continue limited functionality (booking, search — no PHI)

BIOMETRIC AUTH FOR PHI ACCESS:
  Package: local_auth
  Required before:
    - Viewing report detail
    - Downloading report PDF
    - Viewing family health vault documents
    - Accessing AI chat (contains health data)
  Fallback: app PIN (4–6 digit)
  If biometric unavailable: PIN required (no bypass)

SCREENSHOT PREVENTION (sensitive screens):
  Android: FLAG_SECURE on MainActivity (prevents screenshots + screen recording)
  iOS: Blur overlay on app switch (UIApplication.shared.keyWindow)
  Apply to: report detail, report PDF viewer, AI copilot, health score

DEEP LINK VALIDATION:
  Validate all incoming deep links before routing.
  Allowlist of permitted deep link patterns.
  Never auto-navigate from unverified external intents.
  Flutter Android: use intent filters with autoVerify=true

SENSITIVE DATA IN MEMORY:
  Zero-out PHI strings after use where possible.
  Never log health data, report content, or OTPs to console or Crashlytics.
  Use PHI-scrubbing in Serilog sink configuration.

DEPENDENCY SECURITY:
  flutter pub audit run in CI pipeline.
  Flag HIGH/CRITICAL vulnerabilities as pipeline failure.
  Review all new third-party packages before adding.

OFFLINE DATA SECURITY:
